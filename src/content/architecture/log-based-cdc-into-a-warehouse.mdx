Change data capture (CDC) moves the inserts, updates and deletes committed in an operational database into somewhere else, here an analytical warehouse, without querying the tables on a timer. The log-based form reads changes from the database's own transaction log. It is the common way to keep warehouse tables close to a live system, and most of the work is not where the diagram on a vendor's landing page puts it. Reading the log is the easy part. The hard parts are on the warehouse side: changes can arrive twice, deletes have to be handled on purpose, and a restart must not quietly corrupt the target.

This entry is a reference blueprint: a possible design with its assumptions stated, built from the documentation listed under References. It generalises the shape of CDC pipelines I have built and operated, but it is not a diagram of any specific system.

## The blueprint

<Figure figure={logBasedCdc.figures[0]} entry="log-based-cdc-into-a-warehouse" />

The numbered steps in figure 1:

1. **Capture.** A CDC process (for example Debezium or AWS DMS) takes an initial consistent snapshot of the tables, then streams committed changes from the log position it recorded at the snapshot, so no change is missed in between. The snapshot reads the tables themselves. On MySQL, Debezium holds a global read lock while it reads the schemas (its default locking mode), or uses table-level locks where global locks are not permitted.
2. **Transport.** Change events are keyed by the table's primary key. They go either to an event log such as a Kafka topic, or to change files in object storage with an operation column. AWS DMS writing to Amazon S3 adds an `I`, `U` or `D` field to each change record by default; whether full-load rows carry one depends on its `includeOpForFullLoad` setting. It adds no position unless you include a header column:
   - `AR_H_STREAM_POSITION`: the source's stream position, such as an LSN, as a source-dependent string.
   - `AR_H_CHANGE_SEQ`: a unique incrementing number made of a timestamp and a counter.

   Both are empty for full-load rows, and either needs converting into one sortable value.
3. **Land.** The warehouse loads change records into a landing table without modifying them. Each record keeps the key, the operation, the row image, the source log position and the time it was loaded.
4. **Deduplicate.** Each run takes the records loaded since the last successful run and keeps only the latest change per key, ordered by log position.
5. **Merge.** One `MERGE` applies those changes to the current-state tables as inserts, updates and deletes, but only where a change is newer than the position already stored for that key.
6. **Serve.** Models, BI tools and services read the current-state tables, never the landing layer.

## What each part is responsible for

- **Transaction log.**
  - In PostgreSQL, logical decoding reads the write-ahead log (WAL).
  - In MySQL, CDC tools read the binary log, which must use row-based logging. Debezium also requires `binlog_row_image=FULL`.
  - For PostgreSQL 18 and earlier, logical decoding needs `wal_level=logical`. PostgreSQL 19, released on 19 November 2026, needs only `replica` and raises the effective level automatically when the first logical slot is created. As of 21 November 2026, Debezium 3.7 still documents `logical` and is tested against PostgreSQL 14 to 18.
- **Checkpoint.** Capture has to remember where it is.
  - In PostgreSQL that is a replication slot on the server, which holds back the WAL its consumer might still need, even while nothing is connected.
  - In MySQL the capture tool stores its own offset: the binlog file and position, or a GTID set when GTID mode is enabled.
- **Change event log or change files.**
  - With Kafka, events with the same key go to the same partition, and order is guaranteed only within a partition.
  - Object storage files from AWS DMS are written per table and, by default, not in transaction order.
- **Landing table.** Append-only. Keeping raw change records means a run can be repeated, or replayed after a fix, without re-reading the source.
- **Current-state tables.** One row per key, plus the log position of the change that produced it. That position is what makes the rest of the design safe.

## Decisions that matter

### Log-based capture instead of polling

Polling a "last updated" column is simpler, but it cannot see rows that were deleted between polls, and it misses intermediate updates that happen between two runs. Log-based capture sees committed deletes and the versions in between, within the limits listed at the end of this entry, and needs no change to the data model. Polling can still be the right answer when hourly freshness is enough and intermediate versions do not matter.

### Deduplicate before every MERGE

A `MERGE` needs at most one source row per target row. Snowflake returns an error by default when a target row joins several source rows for an update or delete. Worse, duplicate source rows that match no target row are all inserted, silently. BigQuery returns an error when an updating `MERGE` matches more than one source row. A batch of change records nearly always contains several changes for busy keys, so it must be reduced to the latest change per key first.

```sql
-- Snowflake SQL. :window_start is a placeholder for the start of the rows this run reads.
MERGE INTO current_state AS t
USING (
  SELECT key, op, value, log_position
  FROM landing_changes
  WHERE load_id > :window_start
    AND key IS NOT NULL                -- truncate events carry no key; handle them separately
    AND log_position IS NOT NULL
    AND op IN ('c', 'r', 'u', 'd')     -- operation codes normalised when rows land
  QUALIFY ROW_NUMBER() OVER (PARTITION BY key ORDER BY log_position DESC) = 1
) AS s
ON t.key = s.key
WHEN MATCHED AND (t.log_position IS NULL OR s.log_position > t.log_position) AND s.op = 'd' THEN
  UPDATE SET is_deleted = TRUE, log_position = s.log_position
WHEN MATCHED AND (t.log_position IS NULL OR s.log_position > t.log_position) THEN
  UPDATE SET value = s.value, is_deleted = FALSE, log_position = s.log_position
WHEN NOT MATCHED THEN
  INSERT (key, value, is_deleted, log_position)
  VALUES (s.key, IFF(s.op = 'd', NULL, s.value), s.op = 'd', s.log_position);
```

**What the sketch assumes.**

- **`log_position` is a commit-ordered key, not a raw field.** It is one sortable value, built when rows land, with three properties:
  1. for any one key, it increases in the order the source committed the changes;
  2. a change delivered twice gets the same value both times;
  3. two different changes to the same key never share a value.

  What to build it from depends on the source; see "Order by a commit-ordered position" below. Rows with no position, such as AWS DMS full-load rows, get a value that ranks below any streamed change for the same key.
- **Row images are complete.**
  - In PostgreSQL, Debezium leaves values stored with TOAST (PostgreSQL's storage for large field values) out of an update event when they have not changed, unless they are part of the table's replica identity.
  - Either set `REPLICA IDENTITY FULL` on captured tables, or keep the stored value when such a column is missing. Otherwise `UPDATE SET value = s.value` overwrites it.
- **Operation codes are normalised.** Debezium's `c`, `u`, `d` and `r` and DMS's `I`, `U` and `D` are mapped to one set when rows land.
- **No row is skipped between runs.** Choosing which landing rows a run reads needs care: a row stamped before the previous run's cut-off but committed after it would be skipped. Re-reading a small overlap is safe, because the position check ignores anything that is not newer.
- **Deletes for unseen keys are still written.** A delete for a key the target has never seen is written as a deleted marker with its position, for the reason given under "Deletes are a choice".

Before publishing it, I ran the check and the merge in DuckDB, with `CASE` in place of `IFF`. The scenarios were:
- every run in figure 2;
- an insert and delete of a new key in one batch;
- rows with missing keys or positions;
- a PostgreSQL transaction that commits after the snapshot point, keyed by the raw change LSN (the committed update is wrongly rejected) and by the commit-ordered key (it is applied);
- a MySQL snapshot row and a streamed change at the same binlog coordinates, without and with the snapshot rank;
- an exact redelivered duplicate, and a conflicting tie, which stops the run;
- a re-snapshot, at a low placeholder position, at the snapshot's own position, and as a rebuild.

### Order by a commit-ordered position, not by timestamps

In this entry, "log position" means the key defined under "What the sketch assumes": commit-ordered for each key, the same on redelivery, and never shared by two different changes to one key. Positions from the source's log are what both PostgreSQL and Debezium point to for ordering changes and spotting repeats:
- PostgreSQL describes a replication slot as replaying changes in the order they were made on the origin server, and says logical decoding applies changes in commit order.
- Debezium suggests tracking the LSN to decide whether an event is a duplicate.

A raw position is not always that key by itself, so build it per source:
- **MySQL.** For InnoDB tables, MySQL caches a transaction's changes until it commits, so a transaction reaches the binary log only at commit. My reading is that binlog order therefore follows commit order. A single binlog position is not enough, because several rows share one binlog event: build the key from the binlog file's sequence number, the position and the row number together. Debezium gives every snapshot row the same binlog position, read during the snapshot. I assume a streamed change can carry that same position, so rank snapshot rows below streamed changes at equal coordinates.
- **PostgreSQL.** Debezium's `lsn` field is where each change was written in the log, not where its transaction committed. Transactions overlap, so a change can be written before a point in the log and committed after it. My analysis, tested below: a change written before the snapshot point but committed after it carries a lower `lsn` than the snapshot's rows, and a guard on the raw `lsn` would reject a committed update. PostgreSQL's replication protocol sends each transaction's commit LSN, so build the key from the commit LSN first and the change's own `lsn` second. Snapshot rows take the snapshot's position. Debezium also records a `sequence` field holding "the last committed LSN" and the current LSN. Check what your connector version puts there before using it as the key.
- **AWS DMS.** Full-load rows carry no position. For changes, AWS describes `AR_H_CHANGE_SEQ` as a unique incrementing number made of a timestamp and a counter. It does not say that the number follows commit order, so check that for your source before relying on it.

Two more details matter:
- **Debezium's top-level `ts_ms` is not a commit time.** It is when the connector processed the event, on the connector's clock.
- **Equal positions need a rule.** Identical rows at the same position are redelivered duplicates and are harmless. Different rows at the same position for one key mean the key is not unique, and no merge rule can pick the right one, so each run first checks for them and stops if it finds any:

```sql
-- Snowflake SQL. Run before the MERGE; expect no rows. Any row returned stops the run.
SELECT key, log_position
FROM landing_changes
WHERE load_id > :window_start
GROUP BY key, log_position
HAVING COUNT(DISTINCT HASH(op, value)) > 1;
```

AWS DMS takes a different route for change files written to S3: it documents a column holding each change's source commit timestamp (`TimestampColumnName`) for reconstructing order. For full-load rows that column holds the time DMS transferred the row, not a commit time. Changes in the same transaction share a commit time, and timestamps can tie at the clock's resolution, while a log position does not tie. So I prefer the position wherever one is available. That preference is my reasoning, not a documented rule.

### Deletes are a choice

- **What the log carries.** A delete arrives as a delete event, and in Kafka-based pipelines it is followed by a tombstone by default.
- **Hard or soft delete.** Applying it as a hard delete keeps the target small. A soft delete keeps the key and its log position, which lets the same position check stop an old, replayed insert from bringing a deleted row back (run 3 in figure 2). For the same reason, a delete for a key the target has never seen, such as an insert and a delete in one batch, is written as a deleted marker. That trade-off is my analysis.
- **What the log does not carry.** MySQL InnoDB cascade deletes from a foreign key are applied inside the storage engine and are not written to the binary log, so log-based capture never sees them.

### Schema changes need a plan

- **PostgreSQL:** logical decoding carries no DDL, so the connector cannot report schema changes as events.
- **MySQL:** DDL is in the binlog, and Debezium keeps it in an internal schema history topic that is not meant for consumers.

My recommendation:
- Treat additive columns as routine.
- Treat type changes, drops, renames and key changes as reviewed changes, which may need a fresh snapshot.

## Failure and recovery

<Figure figure={logBasedCdc.figures[1]} entry="log-based-cdc-into-a-warehouse" />

**Capture does not skip changes it can read from the log, but some may arrive twice.**
- Debezium's documentation describes exactly-once delivery when the system runs normally, and at-least-once delivery while it recovers from a fault. After a crash, capture resumes from its last committed offset, so recent changes can be delivered again.
- PostgreSQL makes the same point about logical decoding: clients are responsible for handling a message seen more than once.
- Kafka Connect can provide exactly-once delivery for source connectors when configured for it, but that covers only the write into Kafka. Kafka's own documentation notes that exactly-once into another system, such as a warehouse, needs that system's cooperation.
- AWS DMS documents duplicates for S3 targets too, in two cases during the full load phase: when the source table is written intensively, and, with `TargetTablePrepMode` set to `DO_NOTHING`, when a task stops and resumes abruptly.
- Changes can still be lost after capture if loading falls behind the retention of the event log or the change files. That is why load lag is monitored as well as capture lag.

**Figure 2 shows that cooperation.**
- The landing table keeps every duplicate.
- Within a batch, deduplication keeps the newest change per key, so the repeated rows lose.
- Across batches, the merge applies a change only if its log position is newer than the one already stored. Run 3 replays old changes, and the guard rejects them.

Re-running a batch changes nothing, and the target converges on the source once capture catches up. The position check is a design choice, not a product feature.

**When convergence holds.** It depends on at least these conditions, all reasoned from the sources rather than stated by them:
1. Every captured table has a primary key.
2. The log position is a commit-ordered key, as defined above, and the check for equal positions finds nothing.
3. Row images are complete. On PostgreSQL that means accounting for TOAST.
4. The changes are ones the log carries, so no cascade deletes and no truncates.
5. No change is lost to event-log or file retention, and no landing row is skipped between runs.
6. Consumers and reconciliation exclude rows marked deleted.

**When the log has moved on.** If the recorded position is no longer in the log, capture cannot resume from it and needs a new snapshot. That happens when:
- in PostgreSQL, a slot exceeds `max_slot_wal_keep_size` and loses WAL it needed;
- in MySQL, the binlog expires.

**What a new snapshot does not fix:**
- **Deleted rows.** A snapshot contains only rows that still exist, so rows deleted while capture was stopped stay in the target unless the target is rebuilt or reconciled against the snapshot.
- **Updated rows, if snapshot rows carry a low placeholder position.** The position check then rejects them for every key already in the target. Rebuild the target from the snapshot, or give the snapshot rows the position the snapshot recorded.
- **Positions after a MySQL failover.** Debezium documents failing over between MySQL replicas with GTIDs, as long as the new replica has caught up. A binlog file and position, however, point into one server's own log. So my reading is that after a failover, positions from the new server cannot be compared with the stored ones, and the stored positions have to be reset, for example by rebuilding from a snapshot. Otherwise the position check can reject changes without any error. That consequence is my analysis.

## Operating it

**Watch log retention as closely as lag. The risk runs in opposite directions on the two databases:**
- **PostgreSQL:** a slot holds WAL until its consumer catches up, and by default without limit. A stalled consumer fills the source database's disk. Watch `wal_status` and `safe_wal_size` in `pg_replication_slots`.
- **MySQL:** binlogs expire on a timer whatever the consumer's state, and the default depends on where MySQL runs.
  - Self-managed MySQL 8.4 keeps them for 30 days by default.
  - Amazon RDS for MySQL keeps none by default unless `binlog retention hours` is set, to at most 168 hours.

  A consumer that falls further behind than the retention loses its place. Compare capture lag with the setting.
- **Loading:** watch the lag between the event log or change files and the landing table, against their retention.

**Lag metrics:**
- Debezium reports `MilliSecondsBehindSource`, and AWS DMS reports `CDCLatencySource` and `CDCLatencyTarget`.
- Debezium's lag figure includes any clock difference between the database server and the connector.
- AWS states that DMS change capture is not real-time and has no latency SLA.

**Reconcile.** Compare row counts and business totals per table between source and target on a schedule. Duplicates, missed deletes and cascade gaps show up there before anyone else finds them.

## Trade-offs

| Concern | What this design gives | What it costs |
|---|---|---|
| Reliability | Convergence under duplicate delivery, replays and re-runs | Position columns and guard conditions on every table |
| Freshness | Minutes, set by the run schedule | Not suited to sub-second serving |
| Source impact | No polling queries after the snapshot; reads the log | Replication privileges, log retention to watch, and an initial snapshot that reads every table (with locks on MySQL) |
| Cost | Only changed rows move after the snapshot | A landing layer to store and prune |
| Operability | Raw changes are kept, so runs can be repeated | Snapshot and re-snapshot procedures to maintain |

## Alternatives

- **Query-based incremental extraction:** a "last updated" column or ID range.
  - Fewer moving parts and no log access.
  - Misses hard deletes and intermediate versions.
- **Periodic full reloads:**
  - Simplest to reason about.
  - Cost grows with table size, not with change volume.
- **Managed connectors:**
  - Less to operate.
  - The same questions apply about delivery guarantees, deletes and schema changes; read the documentation for each.

## What this blueprint does not cover

- Tables without a primary key. In PostgreSQL, a table published for logical replication without a replica identity rejects `UPDATE` and `DELETE` on the source itself. Without a key, changes cannot be applied per row.
- Generated columns. Debezium 3.7's PostgreSQL documentation says its `pgoutput` plugin does not capture their values. PostgreSQL itself does not publish them by default, and from PostgreSQL 18 stored generated columns can be published with `publish_generated_columns = stored`. Check the connector in use before relying on them.
- MySQL InnoDB cascade deletes, which are not written to the binary log (see "Deletes are a choice").
- `TRUNCATE`, whose events carry no key.
- Low-latency serving, cross-region replication and multi-source joins.
